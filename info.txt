1. What's in the tiles, and what a richer tooltip would cost
The tile carries exactly this per item (decode.js:70-82): qid, lon/lat, drawn title, wiki (lang|title), hasImage, score, pr, qr, cat, sub. Averaged over the pyramid that's 29.9 gzipped bytes per item → 296 MB.

Already paid for, currently unused in the hover:

hasImage — decoded at decode.js:76 and never read anywhere. A 📷 glyph is free.
pr and qr separately — the tooltip collapses them into one "importance"; the split is the interesting part when you're playing with the weight slider.
qid and coordinates — free.
What adding fields would actually cost. I sampled 271 real tiles across all 13 zooms, joined them back to articles.parquet, appended each candidate column to the real payload and re-gzipped, so these are true marginal costs:

Field	encoding	B/item	total	% of 296 MB
country_label	global u16 id	0.10	+1 MB	0.3%
n_sitelinks	u8 clamped	0.23	+2 MB	0.8%
population	log-scaled u16	0.23	+2 MB	0.8%
inception	i16 year	0.33	+3 MB	1.2%
elevation	i16 metres	0.39	+4 MB	1.4%
admin_label	per-tile dict + u8	1.32	+14 MB	4.7%
admin_label	u32 offsets + utf8	3.10	+32 MB	10.9%
descr_en	u32 offsets + utf8	5.59	+58 MB	19.7%
(My extrapolation over-counts items by ~10%, so read the MB column as ~10% high.)

Everything except descr_en is essentially free: all six together are 2.6 B/item, +25 MB, +8% on the tiles and +3% on the whole site. The reason country costs 0.10 B/item is that a tile is almost always one country, so gzip erases the column. admin wants a per-tile string table rather than one string per item — that's the difference between 1.3 and 3.1 B/item.

That buys you a tooltip like:

2,962 m · 47 language editions · importance 41
PageRank 38 · pageviews 44 · 📷
descr_en ("capital of France") is the single best line you could add and the only expensive one at +20%. Restricting it to z ≤ 8 costs only +13 MB and covers everything visible above city zoom, but then the tooltip is inconsistent about when it has a description. I'd rather pay the full +58 MB — and section 2 frees up eight times that.

2. GitHub Pages
The documented limits: 1 GB published site (hard), 1 GB recommended source repo, 100 GB/month bandwidth (soft), 10 builds/hour, and it's "not intended for commercial operations".

Your payload today:

files	bytes
data/tiles/	98,755	296 MB
data/search/	84,682	520 MB
total	183,437	816 MB
It fits, with 22% headroom. Five things would bite:

It won't survive a second data build. Every pipeline rerun rewrites all 183k files, and git keeps the old ones forever. The tiles are already gzipped so git can't recompress them. Run the pipeline twice and the repo is past its recommended size; four times and you're in trouble that only a history rewrite fixes.
The search index is 64% of the site and mostly dead weight. 59,518 level-3 shards: median 77 bytes, p90 3.4 KB, p99 146 KB, max 7.65 MB. 2,023 shards hold 369 of the 424 MB. Meanwhile search.js:7 renders 12 results and re-ranks inside the shard — so someone typing three common letters downloads 7.65 MB to look at twelve rows.
183k files makes clone, git status and push slow, especially from a network share.
Bandwidth is fine until it isn't. A cold visit costs ~1 MB of your bytes (10 KB html + 45 KB src + 4 KB manifest + 207 KB of zoom indexes + 289 KB gzipped search manifest + 200-500 KB of tiles), so 100 GB ≈ 100k visits. One front-page day plus a few fat search shards changes that arithmetic fast.
unpkg. index.html:11-13 pulls ~2.2 MB of maplibre + deck.gl from a third-party CDN. Their outage is your white screen. Vendor both files.
Fix (2) first and everything else relaxes. Capping each level-3 shard (entries are already score-sorted) and gzipping them, reusing the maybeGunzip helper that already exists at decode.js:19:

cap	raw total	~gzipped	shards truncated
none	424 MB	—	—
32 KB (~500 entries)	118 MB	~35 MB	1,929
8 KB (~130 entries)	55 MB	~16 MB	4,064
I'd take the 32 KB cap: site goes 816 MB → ~330 MB, worst-case keystroke goes 7.65 MB → 32 KB, and you keep enough tail that an obscure exact-prefix match still survives. Also gzip or drop the search manifest (1.26 MB raw, 289 KB gzipped, paid by every visitor before they type anything — a 404-driven fallback to shorter prefixes would cost one wasted request instead).

After that, GitHub Pages is genuinely comfortable, and you can afford descr_en in the tiles.

3. Shared hosting vs Pages
GitHub Pages	your shared host
CDN	yes (Fastly)	no — one origin
re-publishing data	grows history ~800 MB each time	rsync overwrites in place
file count	fine	check your inode quota — 183k files breaches many plans
upload	git push	hours over FTP; use rsync/SSH, or upload a tar and extract
headers	fixed	yours (Content-Encoding, Cache-Control, CORS)
size cap	1 GB	your plan
Neither is strictly better: shared hosting wins on iteration, Pages wins on audience. The combination that beats both is Pages for the site (a few hundred KB) + the data in an object store with free egress — Cloudflare R2 with a public bucket is the usual answer (no file-count limit, no egress charge; you'd need CORS on the bucket and an absolute DATA_URL in main.js:17). Note Cloudflare Pages is out — it caps at 20,000 files.

The structural fix, if you want this bulletproof on any host: pack the tiles into one file addressed by HTTP Range, PMTiles-style. 98,755 files → 1, and your per-zoom index becomes the offset table. Fastly, Apache and nginx all serve ranges. It's a day of work and it makes the file-count question disappear permanently.

4. The basemap
You're on CARTO positron/dark-matter no-labels with no API key, and attribution does render (I confirmed "© CARTO, © OpenStreetMap contributors" in the screenshot). But CARTO's own docs say commercial use needs an Enterprise licence and free use is for "CARTO grantees" — there's no documented anonymous tier. basemaps.cartocdn.com works because it's unauthenticated, not because you're entitled to it; the historically quoted non-commercial allowance was 75,000 mapviews/month. For an MPIDR research map that's probably fine, and you could apply for a grant, but a viral day could get you rate-limited with no warning.

OpenFreeMap is the low-friction swap: no API key, no registration, explicitly "no limits on the number of map views or requests", commercial use allowed, self-hostable, donation-funded (so: no SLA). Attribution required — "OpenFreeMap © OpenMapTiles Data from OpenStreetMap". One caveat that matters for you: there's no nolabels variant, so you'd fetch the style JSON and drop layers with a layout['text-field'] before passing it as mapStyle. About ten lines, and it also lets you dark-mode the style yourself.

Other options: MapTiler/Stadia have real free tiers but put a scrapeable key in your public page (domain-lock it). Protomaps if you want to self-host a .pmtiles. And since your basemap is only a backdrop, a Natural Earth land+coastline GeoJSON (~1 MB) in a deck.gl layer would remove the external dependency entirely below z≈7. Don't point at tile.openstreetmap.org — their usage policy forbids it.
